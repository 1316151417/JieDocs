# 《我是如何使用 LLM 的》— 深度分析报告

> 源视频：Andrej Karpathy, "How I use LLMs" (2025)
> 分析维度：认知框架、能力光谱、工具生态、交互模态、工作流、策略选择

---

## 一、核心认知模型：Karpathy 的 LLM 心智框架

Karpathy 在整个视频中反复使用几个关键隐喻来构建对 LLM 的理解。这些隐喻不是修辞装饰，而是他做出每个使用决策的认知基础。

### 1.1 "Zip 文件"隐喻

**核心命题**：LLM 本质上是对互联网知识的有损概率压缩。

| 维度 | 含义 | 实践影响 |
|------|------|---------|
| **有损性** | 无法精确还原训练数据，只能保留"要旨"和"感觉" | 模型输出不可盲信，需要验证 |
| **概率性** | 输出是统计推断而非确定计算 | 同一问题可能得到不同答案；需要交叉验证 |
| **知识截止** | 预训练时间点之后的知识完全缺失 | 近期信息必须通过搜索工具补充 |
| **频率偏差** | 高频出现的知识记忆好，冷门知识记忆差 | 常见问题（如药品成分）可信度较高；小众话题需要警惕 |

**Karpathy 的实践原则**：
- 高频常识→可直接信任模型内建知识（如"美式咖啡有多少咖啡因"）
- 低频/小众知识→需要上传文档或启用搜索工具
- 近期信息→必须使用搜索工具

### 1.2 Token 流与上下文窗口

**核心机制**：与 LLM 的交互本质上是人与模型协作构建一个一维 Token 序列。

**关键洞察**：
- 聊天气泡只是 UI 表象；底层是 Token 轮流写入同一个流
- 上下文窗口 = 模型的"工作记忆"——Token 是珍贵的有限资源
- 用户与模型交替写入 Token，特殊 Token 标记控制权的移交

**Karpathy 的黄金规则**：
1. 切换话题时**必须**开启新聊天（清空上下文窗口）
2. 无关 Token 是噪音——既降低准确度，又增加推理成本
3. 只在 Token 对当前任务有贡献时才保留

### 1.3 预训练与后训练的分工

Karpathy 将模型能力明确区分为两个来源：

```
预训练阶段                      后训练阶段
──────────                    ──────────
数据：整个互联网               数据：人类构建的对话示例
产出：世界知识                 产出：助手人格
成本：数千万美元/数月          成本：相对较低
频率：极低（数月~一年一次）     频率：可更频繁迭代
特征：模糊、有截止日期          特征：风格、形式、对话能力
```

**实践意义**：这个分工解释了为什么模型"知道很多但不会主动用"——知识在预训练中获得，但表达方式在后训练中塑造。也解释了为什么搜索工具至关重要——它弥合了知识截止日期与实时信息需求之间的鸿沟。

## 二、模型能力光谱：从基础模型到思考模型

### 2.1 两类模型的本质差异

| | 基础模型（如 GPT-4o） | 思考模型（如 o1/o3/Grok-Think） |
|---|---|---|
| **训练** | 预训练 + SFT | 预训练 + SFT + **强化学习** |
| **推理方式** | 一次前向，快速给出答案 | 多步推理，类似人类"内心独白" |
| **响应速度** | 秒级 | 分钟级 |
| **适用场景** | 写作、翻译、简单问答 | 数学、编程、复杂推理 |
| **token 消耗** | 低 | 高（大量内部思考 token） |

### 2.2 Karpathy 的使用策略

**决策树**：
1. 先用非思考模型（快速、低成本）
2. 如果结果不理想→切换到思考模型
3. 简单任务（旅行建议、日常问答）永远不需要思考模型

**关键案例**：梯度检查 Bug 调试
- GPT-4o："给了一堆不解决核心问题的建议"
- o1 Pro：思考 1 分钟后精确定位参数打包/解包不匹配的 Bug
- Claude 3.5 Sonnet（非思考模型）：同样解决了问题——说明并非只有思考模型才能做好推理
- Gemini、Grok 3 也能解决——多模型交叉验证的策略奏效

### 2.3 厂商思考模型对比

| 厂商 | 思考模型 | 特点 |
|------|---------|------|
| OpenAI | o1 / o3-mini / o1 Pro | 最早推出，o1 Pro 需 $200/月 |
| DeepSeek | R1 | 第一个公开发表强化学习推理论文，可通过 Perplexity 访问 |
| Anthropic | Claude 3.7 Extended Thinking | 视频录制时刚推出 |
| xAI (Grok) | Grok 3 + Think 开关 | 界面友好，显示思维过程 |

**关键观察**：Karpathy 特别推崇 DeepSeek R1 的透明性——它在 Perplexity 中展示了完整的"原始思考过程"，而 OpenAI 只给出摘要。

## 三、工具使用矩阵：LLM 的能力外延

### 3.1 互联网搜索

**问题**：模型知识有截止日期，无法回答近期问题。

**机制**：模型发出特殊搜索 token → 应用执行搜索 → 网页文本注入上下文窗口 → 模型基于新鲜信息回答。

**Karpathy 的使用决策**：
- ⚡ 满足以下任一条件时启用搜索：
  1. 信息具有时效性（近期事件、最新产品）
  2. 话题较为小众（不确定模型训练数据中覆盖程度）
  3. 答案可能随时间变化（股价、产品功能）
- ⚡ 高频常识问题不需要搜索
- ⚡ 在已知需要搜索时，主动点击搜索按钮（而非依赖模型自动判断）

**各平台搜索能力差异**（录制时）：
- ChatGPT：需主动启用或模型自动检测
- Perplexity：原生搜索体验最佳，Karpathy 仍习惯用此
- Claude：当时不支持搜索
- Gemini 2.0 Flash：有搜索，但 Pro 版本反而不支持
- Grok：自动检测并搜索

### 3.2 Python 解释器 / 代码执行

**问题**：LLM 不擅长精确计算——大数乘法等任务在"脑中"完成容易出错。

**机制**：模型编写程序 → 发出特殊执行 token → 环境运行代码 → 结果返回上下文窗口 → 模型基于结果回答。

**关键演示**：
- 简单乘法（30×9）：模型直接给出正确答案——无需工具
- 大数乘法：模型自动转向 Python 解释器
- Grok 3 缺乏代码执行能力→在"脑中"做大数乘法→结果极其接近但最后几位错误

**平台差异**：
| 平台 | 代码执行 | 备注 |
|------|---------|------|
| ChatGPT | Python 解释器 | 训练时内置工具使用模式 |
| Claude | JavaScript 代码 | 在浏览器环境中运行 |
| Grok 3 | ❌ | 会尝试"脑算"，可能出错 |
| Gemini 2.0 Pro | ❌ | 大数乘法"脑算"错误 |

### 3.3 深度研究（Deep Research）

**定位**：互联网搜索 + 思考模型 + 长时间运行（数十分钟）的复合工具。

**适用场景**：
- 产品对比研究（如 Brave vs Arc 浏览器隐私性）
- 成分/补剂研究（如 Ca-AKG 的功效与安全性）
- 学术调研（如小鼠寿命延长技术汇总）

**Karpathy 的评价**：
- ChatGPT 的深度研究（$200/月 Pro 功能）：最详尽、可读性最好、引用最丰富
- Perplexity 和 Grok 的版本：较简短，细节不如 ChatGPT 版
- **关键警告**：结果不可盲信——他分享了一个"美国 LLM 实验室"表格的失败案例，其中遗漏了 xAI，错误包含了 HuggingFace，数字也可能不准确

**使用策略**：作为"第一稿"和文献索引——通过引用反查原始来源进行验证。

### 3.4 文件上传与文档协作阅读

**核心价值**：将具体文档注入上下文窗口，使模型从"模糊记忆"切换到"精确引用"模式。

**Karpathy 的杀手级应用**：与 LLM 一起读书。

**读书工作流**：
1. 从古腾堡计划等来源找到书的全文
2. 复制章节粘贴到 Claude/ChatGPT
3. 先要求总结（建立全局认知）
4. 边读边问——遇到不懂的段落即时提问
5. 可要求创建概念图（Mermaid 图表）

**关键洞察**：
- 对于古老文本（如 1776 年的《国富论》）、跨领域文献（如生物学论文），LLM 极大降低了阅读门槛
- Karpathy 声称"几乎不再独自读书"
- 他遗憾当前缺乏无缝的"高亮即问"阅读工具——现有方案依赖笨拙的复制粘贴

## 四、多模态交互全景

### 4.1 语音交互的两层架构

Karpathy 区分了两种本质不同的语音模式：

| | "假音频"（语音转文本） | "真音频"（高级语音模式） |
|---|---|---|
| **机制** | ASR→文本→LLM→文本→TTS | 音频 Token 直接进入模型 |
| **模型处理** | 文本 token | 音频 token |
| **能力** | 标准文本能力 | 可理解语调、情感、语速；可模仿声音 |
| **延迟** | 较低 | 极低（端到端） |
| **典型产品** | 所有平台的语音输入 | ChatGPT Advanced Voice / Grok Voice |

**Karpathy 的使用习惯**：
- 约 50% 的查询使用语音输入（桌面端用 Super Whisper 系统级工具）
- 手机端约 80% 使用语音——"懒得打字"
- 高级语音模式主要用于演示和娱乐——他认为它"太保守，拒绝太多"

### 4.2 Grok 语音模式对比

Karpathy 特别展示了 Grok 语音的多模式切换，用于说明不同厂商的差异化：

| 模式 | 特点 |
|------|------|
| 默认 | 标准语音助手 |
| 浪漫 | 调情式对话 |
| 放肆 | 粗鲁直接 |
| 阴谋论 | 戏谑地讨论阴谋论 |
| 性感 | 情色叙事 |

**差异点**：OpenAI 的语音极其保守，拒绝大量请求；Grok 则"什么都敢说"。Karpathy 认为这种差异本身就是用户选择的重要维度。

### 4.3 图像能力

**图像输入（OCR + 理解）**：
- 机制：图像→切分成 Patches→量化为视觉 Token→与文本 Token 混合输入
- 关键应用：营养标签解读、血液检测报告分析、牙膏成分审查、梗图解释
- **黄金实践**：先要求转录为文本（验证模型"看到"了什么），再基于文本提问

**图像输出（生成）**：
- 机制：目前是两阶段——LLM 生成描述→独立图像生成模型（如 DALL-E 3）生成图像
- 使用场景：YouTube 缩略图、图标、概念可视化
- 工具：DALL-E 3、Ideogram（Karpathy 交替使用）

### 4.4 NotebookLM 播客生成

**独特价值**：将任意文档/网页转换为自然对话式播客。

**Karpathy 的使用场景**：
- 被动学习：散步/驾车时收听
- 利基话题：没有现成人类播客覆盖的主题
- 他制作了整季播客"谜团的历史"并上传到 Spotify

### 4.5 视频能力

**视频输入**：当前主要为移动端高级语音模式 + 摄像头
- 实际实现可能仍是截图序列（如每秒一帧）而非真正的视频流
- Karpathy 认为这对非技术用户（如长辈）特别有价值——"指着东西问"

**视频输出**：快速演进中（Sora、Veo 2 等）
- Karpathy 非重度用户（"不在创意行业"）

## 五、开发者工作流：从 UI 到 IDE

### 5.1 Cursor 与 Composer 范式

**核心转变**：从"在网页中要代码片段"到"AI 代理直接在代码库上工作"。

**演进路径**：
```
阶段 1: Ctrl+K → 修改单行代码
阶段 2: Ctrl+L → 解释代码块
阶段 3: Ctrl+I (Composer) → 自主代理，跨文件编辑
阶段 4: Composer Agent → 执行命令、安装依赖、自主调试
```

### 5.2 Vibe Coding 理念

**定义**（Karpathy 创造）：将控制权交给 Composer，用自然语言描述需求，让 AI 完成实现。

**核心理念**：
- 你不再逐行编码，而是"发号施令"
- 最坏情况：随时可回退到传统编程（所有文件都是标准代码，完全可控）
- AI 是"非常高效的初级开发者"，但你仍然是架构师

**实战演示**：井字棋应用
- 5 句话创建完整 React 应用
- "加彩纸效果"→自动安装 react-confetti 库
- "加胜利音效"→自动找到在线音效 URL 并集成
- Karpathy 自己也惊讶于音效功能的顺利运行

### 5.3 与 ChatGPT/Claude Web UI 的分工

| 场景               | 工具选择                           |
| ---------------- | ------------------------------ |
| 代码片段/算法思路        | ChatGPT Web                    |
| 图表生成/数据分析        | ChatGPT Advanced Data Analysis |
| 原型应用/图表（Mermaid） | Claude Artifacts               |
| 专业编程/多文件项目       | Cursor + Composer              |
| 文档协作阅读           | Claude（文件上传体验较好）               |

## 六、个性化与质量提升策略

### 6.1 提示词策略

**核心原则**：少样本 > 零样本。

Karpathy 在构建自定义 GPT 时的模式：
1. 先描述任务（零样本部分）
2. 再给出 4 个具体示例（少样本部分）
3. 使用 XML 标签结构化长示例

**为什么有效**：Karpathy 类比为"教人类——用言语解释远不如用实例示范有效"。

### 6.2 自定义 GPT 体系

**Karpathy 的三个自建 GPT**：

| GPT 名称 | 功能 | 设计模式 |
|----------|------|---------|
| 韩语词汇提取器 | 句子→词汇字典（韩语;英语格式） | 少样本提示 + 固定输出格式 |
| 韩语详细翻译器 | 逐词分解翻译，保留所有语法颗粒 | 少样本 + XML 结构 + 多轮指令 |
| 韩语字幕助手 | 截图→OCR→翻译→分解 | 上下文预设（告知剧名和场景类型） |

**本质**：自定义 GPT = 将复用提示词固化为可重复调用的"应用"。

### 6.3 记忆系统

**ChatGPT Memory 机制**：
- 在对话中提取关于用户的信息
- 以文本摘要形式存储
- 每次新对话自动前置到上下文窗口

**Karpathy 的观察**：
- 初期怀疑→逐渐认可
- "ChatGPT 确实越来越了解我了"
- 特别有利于个性化推荐（如电影推荐）
- 可手动编辑/删除记忆——"我的记忆太私密了不想展示"

### 6.4 自定义指令

**Karpathy 的设置**：
- "不要像 HR 业务伙伴那样说话——正常跟我交流"
- "给我解释、教育和洞察"
- 韩语学习：设定默认敬语等级

**本质**：全局系统提示词，影响所有对话。

## 七、生态全景与选择策略

### 7.1 主要玩家定位（录制时）

| 产品             | 定位        | 核心优势                                | 主要短板                  |
| -------------- | --------- | ----------------------------------- | --------------------- |
| **ChatGPT**    | 先行者、功能最全  | 功能最丰富；深度研究独一档；记忆系统独有                | 语音偏保守                 |
| **Claude**     | 最强竞争者     | Artifacts 独有（应用/图表生成）；代码能力强；文件上传体验好 | 当时无搜索；无深度研究           |
| **Gemini**     | Google 生态 | 与 Google 服务集成                       | 功能碎片化（Pro 反而缺搜索）      |
| **Grok**       | 娱乐差异化     | 语音模式最"放得开"；界面友好                     | 缺乏代码执行；深度研究不如 ChatGPT |
| **Perplexity** | 搜索优先      | 原生搜索体验最佳；托管 DeepSeek R1             | 非通用助手                 |
| **DeepSeek**   | 中国开源力量    | 强化学习推理论文开先河                         | 通过第三方访问               |
| **NotebookLM** | 播客生成      | 独一无二的文档→播客转换                        | 功能单一                  |

### 7.2 Karpathy 的"LLM 委员会"策略

**核心实践**：对同一问题问多个模型。

**使用场景**：
- 重要决策前（如旅行目的地选择——Claude 和 Gemini 都推荐采尔马特）
- Bug 调试（测试 GPT-4o→o1 Pro→Claude→Gemini→Grok→DeepSeek R1）
- 了解不同模型的"观点"

**多模型策略的价值**：
- 交叉验证答案的正确性
- 比较不同模型的推理质量
- 当某个模型拒绝回答时，另一个可能愿意

### 7.3 模型选择决策框架

结合 Karpathy 的使用模式，可归纳出以下决策树：

```
任务类型？
│
├─ 日常问答/写作 ──→ 非思考模型（GPT-4o/Claude Sonnet）
│   └─ 有近期信息需求？ ──→ 启用搜索工具
│
├─ 编程/数学/推理 ──→ 先试非思考模型
│   └─ 未解决？ ──→ 切换思考模型（o1/o3/Grok Think）
│
├─ 深度调研 ──→ Deep Research（ChatGPT Pro）
│
├─ 文档阅读/分析 ──→ 上传到 Claude/ChatGPT
│   └─ 想要播客？ ──→ NotebookLM
│
├─ 原型应用/图表 ──→ Claude Artifacts
│
├─ 专业软件开发 ──→ Cursor + Composer
│
├─ 数据分析/绘图 ──→ ChatGPT Advanced Data Analysis
│
└─ 语言学习 ──→ 自定义 GPT
```

## 八、关键洞察与启示

### 8.1 Karpathy 的核心哲学

1. **模型是工具，不是权威**：反复强调"不保证正确"、"作为第一稿"、"通过引用验证"——这在视频中出现了超过 20 次。这是贯穿全文的最强信号。

2. **Token 是货币**：上下文窗口中的每个 Token 都有成本（注意力分散 + 推理延迟 + 金钱成本）。节俭地管理 Token 是高效使用 LLM 的基本功。

3. **分层使用策略**：从免费模型→付费旗舰→思考模型→深度研究，根据任务复杂度逐层升级，不滥用高级功能。

4. **工具组合主义**：没有一个应用是完美的。Karpathy 同时付费使用多个服务，在不同场景切换不同工具。

5. **人机协作而非替代**：即使是 Vibe Coding，也保留了"可以回退到传统编程"的安全网。AI 是"初级分析师"、"初级开发者"，人是监督者和架构师。

### 8.2 值得跟踪的技术趋势

视频中暗示/预测的几个方向：

- **思考模型民主化**：从 DeepSeek 开源论文到各厂商跟进，强化学习推理将成为标配
- **工具集成的深化**：模型将获得越来越多的工具（浏览器、代码执行、文件系统）
- **多模态统一**：音频/图像/视频的原生 Token 化处理（Omni 模型）
- **Agent 化**：从 Composer Agent 到更自主的代码代理
- **个性化记忆**：跨对话的状态保持将越来越成熟
