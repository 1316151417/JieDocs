# Node.js / npm / TypeScript 核心笔记

## 1. 全局心智模型

```
JavaScript
    │
    │ 语言
    ↓
TypeScript
    │ JS + 类型系统，最终转成 JS
    ↓
Node.js
    │ JS Runtime，提供文件、网络、进程等系统能力
    ↓
npm / pnpm
    │ 包管理 + 工程管理
    ↓
npm Registry
    │ 公共软件包仓库
    ↓
第三方生态
```

核心关系：

```
Node.js
├── node        JS Runtime
├── npm         默认包管理器
└── npx         npm package CLI 的便捷执行入口

TypeScript
└── tsc         TS 编译器，通过 npm/pnpm 安装

pnpm
└── npm 的替代包管理器
```

---

# 2. JavaScript、TypeScript、Node.js

## JavaScript

JavaScript 是**语言**，不是需要安装的软件。

真正执行 JS 的是 Runtime：

```
浏览器
└── JS Engine + Web API

Node.js
└── JS Engine + Node API
```

浏览器执行：

```
console.log("hello");
```

终端执行：

```
node hello.js
```

---

## Node.js

Node.js 解决：

> JavaScript 脱离浏览器后的运行环境问题。

除了执行 JS，还提供：

```
文件系统
网络
进程
环境变量
Stream
Event
子进程
CLI
...
```

所以它尤其适合：

```
Web 后端
CLI
构建工具
Coding Agent
桌面工具的核心逻辑
```

---

## TypeScript

TypeScript：

> JavaScript + 静态类型系统。

最终仍然需要变成 JavaScript：

```
foo.ts
  ↓
TypeScript Compiler
  ↓
foo.js
  ↓
Node.js
```

它给开发者两种选择：

```
简单、小型、快速开发
→ JavaScript

大型、长期维护工程
→ TypeScript
```

TypeScript 本身是普通 npm package，通常作为项目开发依赖：

```
npm install -D typescript
```

执行：

```
npx tsc
```

不建议为了项目开发全局安装 TypeScript，因为不同项目可能使用不同版本。

# 3. npm 的本质

npm 可以理解为 Node 生态的统一工程入口：

```
npm
├── 依赖管理
├── package.json
├── lockfile
├── scripts
├── CLI 分发
├── Workspace / Monorepo
├── npm Registry
└── publish
```

npm 安装 Node.js 时通常一起安装：

```
node -v
npm -v
npx -v
```

# 4. package.json

`package.json` 是一个 Node package / 项目的核心描述文件。

典型：

```
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",

  "scripts": {
    "build": "tsc",
    "test": "vitest"
  },

  "dependencies": {
    "xxx": "^1.0.0"
  },

  "devDependencies": {
    "typescript": "5.9.3"
  }
}
```

核心理解：

```
package.json
├── 我是谁
├── 我依赖谁
├── 如何开发/构建我
├── 我对外暴露什么
└── 我如何运行
```

---

# 5. dependencies 与 devDependencies

## dependencies

程序**运行时**需要：

```
{
  "dependencies": {
    "openai": "..."
  }
}
```

## devDependencies

仅开发、构建、检查需要：

```
{
  "devDependencies": {
    "typescript": "...",
    "biome": "...",
    "esbuild": "..."
  }
}
```

例如：

```
typescript
esbuild
biome
husky
@types/node
```

通常属于开发基础设施。

---

# 6. Monorepo 为什么根 package.json 可能只有 devDependencies

例如：

```
pi-monorepo/
├── package.json
├── package-lock.json
└── packages/
    ├── ai/
    │   └── package.json
    ├── agent/
    │   └── package.json
    └── coding-agent/
        └── package.json
```

根：

```
{
  "private": true,
  "workspaces": ["packages/*"]
}
```

意味着根项目主要负责：

```
工程管理
构建
测试
Lint
Workspace
版本管理
```

真正的软件包依赖由：

```
packages/ai/package.json
packages/agent/package.json
...
```

分别声明。

因此：

> 根 package.json 没有 dependencies，不代表整个项目没有运行依赖。

# 7. npm Workspace

Workspace 用来管理 Monorepo：

```
一个 Git 仓库
   ↓
多个 npm package
```

例如：

```
{
  "workspaces": [
    "packages/*"
  ]
}
```

可以：

```
npm run build --workspaces
```

对所有 workspace 执行 build。

或者：

```
npm run test --workspace=@scope/pi-ai
```

只操作一个 workspace。

整个 Monorepo 通常共享根：

```
package-lock.json
```

记录完整依赖树。

---

# 8. npm scoped package

例如：

```
@earendil-works/pi-ai
```

结构：

```
@earendil-works / pi-ai
└──── scope ───┘   └ package
```

类似于 namespace。

作用：

```
归属识别
命名空间隔离
组织管理
避免普通包名冲突
```

例如：

```
@company/core
@company/agent
@company/cli
```

Workspace 内也可以：

```
import xxx from "@company/core";
```

npm 会解析到对应 workspace。

---

# 9. package-lock.json

区别：

```
package.json
→ 允许安装什么

package-lock.json
→ 实际确定安装什么
```

例如：

```
{
  "dependencies": {
    "foo": "^1.2.0"
  }
}
```

意味着允许一定范围内升级。

而 lockfile 会记录：

```
foo = 1.2.7

以及 foo 的所有间接依赖具体版本
```

目的：

> 可复现构建。

保证：

```
我的电脑
同事电脑
CI
生产环境
```

尽可能使用同一套依赖树。

应用项目通常应该提交 lockfile。

# 10. npm install 与 npm ci

## npm install

日常开发：

```
npm install
```

根据：

```
package.json
+
package-lock.json
```

解析并安装依赖，必要时可能更新 lockfile。

## npm ci

CI / 干净环境：

```
npm ci
```

核心：

> 严格按照 package-lock.json 恢复依赖。

特点：

```
删除原 node_modules
严格使用 lockfile
不修改 lockfile
package.json 与 lock 不一致直接失败
```

所以 CI 常见：

```
npm ci
npm run build
npm test
```

# 11. scripts：项目任务

package.json：

```
{
  "scripts": {
    "build": "tsc",
    "test": "vitest",
    "check": "biome check ."
  }
}
```

执行：

```
npm run build
npm run check
npm test
```

本质：

> scripts 定义“这个项目有哪些任务”。

类似：

```
Makefile task
Gradle task
```

名字基本由项目自己定义。

因此：

```
npm run check
```

通常不是 npm 内置检查能力，而是执行：

```
package.json → scripts.check
```

# 12. bin：Package 提供的 CLI

例如开发一个 CLI：

```
{
  "name": "zhoujie-awesome-cli",
  "bin": {
    "zhoujie": "./cli.js"
  }
}
```

含义：

> 这个 package 对外提供一个名叫 `zhoujie` 的 CLI。

注意区别：

```
scripts
→ 项目的任务

bin
→ package 对外提供的程序
```

---

# 13. scripts 与 bin 的核心关系

```
package.json
│
├── scripts
│      ↓
│   npm run
│
└── bin
       ↓
   npm exec / npx
```

例如：

```
{
  "scripts": {
    "build": "tsc"
  }
}
```

执行：

```
npm run build
```

而 TypeScript package 本身声明：

```
{
  "bin": {
    "tsc": "./bin/tsc"
  }
}
```

于是：

```
npm run build
    ↓
scripts.build
    ↓
"tsc"
    ↓
node_modules/.bin/tsc
    ↓
TypeScript package 的 bin
```

所以：

> `npm run` 的直接目标是 script；script 内部又经常调用其他 package 提供的 bin。

---

# 14. npm exec 与 npx

直接执行 package 提供的 CLI：

```
npm exec -- tsc
```

更常见的便捷形式：

```
npx tsc
```

可以简单记：

```
npm run
→ 执行 scripts

npm exec
→ 执行 package executable/bin

npx
→ npm exec 的便捷 CLI 使用方式
```

---

# 15. npx 解决什么问题

核心：

> 快速执行 npm package 提供的 CLI。

例如：

```
npx tsc
npx eslint
npx create-vite
```

它解决两个主要问题。

## 项目 CLI

项目已经安装 TypeScript：

```
npm install -D typescript
```

直接：

```
npx tsc
```

使用项目对应版本，而不是全局版本。

## 一次性 CLI

例如：

```
npx create-vite
```

即使没有提前显式安装，也可以获取 package 后运行。

适合：

```
项目初始化器
代码生成器
临时工具
```

# 16. node_modules/.bin

npm package 可以声明：

```
{
  "bin": {
    "tsc": "./bin/tsc"
  }
}
```

安装后 npm 会建立类似：

```
node_modules/
├── typescript/
│   └── bin/tsc
│
└── .bin/
    └── tsc
```

所以：

```
npx tsc
```

最终会找到对应 executable。

`npm run` 执行 script 时，也会自动把：

```
node_modules/.bin
```

加入临时 $PATH。

所以：

```
{
  "scripts": {
    "build": "tsc"
  }
}
```

不需要写：

```
"build": "npx tsc"
```

---

# 17. JS 文件为什么可以作为 bin

CLI 入口通常：

```
#!/usr/bin/env node

console.log("hello");
```

关键是：

```
#!/usr/bin/env node
```

这是 shebang。

表示：

> 使用 Node.js 解释执行当前文件。

概念上：

```
./cli.js
```

最终相当于：

```
node cli.js
```

所以 `bin` 写：

```
{
  "bin": {
    "zhoujie": "./cli.js"
  }
}
```

而不是：

```
{
  "bin": {
    "zhoujie": "node ./cli.js"
  }
}
```

因为：

```
scripts 的值
→ shell command

bin 的值
→ executable 文件路径
```

---

# 18. `/usr/bin/env node`

`env` 是 Unix 程序：

```
/usr/bin/env
```

一个重要能力：

> 根据当前 $PATH 查找程序并执行。

所以：

```
/usr/bin/env node
```

相当于：

```
读取 PATH
   ↓
寻找 node
   ↓
执行 node
```

比：

```
#!/usr/bin/node
```

更灵活，因为 Node 可能实际位于：

```
/opt/homebrew/bin/node

或者

~/.nvm/.../bin/node
```

因此 Node CLI 通常：

```
#!/usr/bin/env node
```

# 19. npm Registry

npm Registry 类似：

> Node/npm 世界的公共软件包仓库。

可以粗略类比：

```
Maven Central ↔ npm Registry
```

完整链路：

```
开发者
  ↓
npm publish
  ↓
npm Registry
  ↓
npm install / npx
  ↓
其他开发者
```

npx 并不是去 GitHub 搜索代码。

```
GitHub repository
        ≠
npm package
```

通常需要把项目发布为 npm package，才能：

```
npx package-name
```

# 20. 发布 npm package

不是匿名发布。

基本流程：

```
注册 npm 账号
    ↓
完成认证/安全配置
    ↓
npm login
    ↓
npm whoami
    ↓
准备 package.json
    ↓
npm publish
```

例如：

```
{
  "name": "@zhoujie/awesome-cli",
  "version": "1.0.0",
  "bin": {
    "awesome": "./cli.js"
  }
}
```

发布后其他人可以：

```
npx @zhoujie/awesome-cli
```

# 21. npm Registry 的开放性与安全

公共 npm Registry 发布门槛较低。

优点：

```
生态发展快
个人工具容易分发
CLI 分发极其方便
```

代价：

```
恶意 package
供应链攻击
typosquatting
账号被盗
依赖污染
```

因此：

```
npx random-package
```

本质上应该理解成：

> 获取互联网上其他人的程序并在自己机器执行。

不要随意执行陌生 package。

scope：

```
@zhoujie/xxx
```

除了组织管理，也是重要的 namespace，可以降低名称冲突问题。

# 22. pnpm

pnpm 是 npm 的替代包管理器。

```
                 Node 生态
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
       npm         pnpm        yarn
```

它们主要都围绕：

```
package.json
npm package
npm Registry
dependencies
scripts
workspace
lockfile
```

不是三个完全不同的生态。

---

## pnpm 的核心价值

### 更高效的依赖存储

传统模式容易出现：

```
project-A → lodash
project-B → lodash
project-C → lodash
```

多份重复文件。

pnpm 使用 content-addressable store：

```
           pnpm store
               │
          lodash@版本
          ↙    ↓    ↘
         A     B     C
```

相同 package 内容可以复用。

### 更严格的依赖关系

减少“项目没有声明某依赖，却因为 hoisting 偶然能够 import”的问题。

# 23. npm 与 pnpm 常用对应

```
npm install
↔ pnpm install

npm install xxx
↔ pnpm add xxx

npm install -D xxx
↔ pnpm add -D xxx

npm uninstall xxx
↔ pnpm remove xxx

npm run build
↔ pnpm build

npm exec xxx
↔ pnpm exec xxx

npx xxx
↔ pnpm dlx xxx

package-lock.json
↔ pnpm-lock.yaml
```

当前阶段掌握 npm 即可，遇到 pnpm 项目再映射命令。

# 24. Node / TS 推荐安装模型

推荐：

```
Node.js
├── node
├── npm
└── npx

项目
├── TypeScript
├── eslint/biome
├── esbuild
└── 其他工具
```

即：

**系统层面：**

```
Node.js
```

**项目层面：**

```
TypeScript 等开发工具
```

不要为了方便把大量项目工具全部全局安装。
