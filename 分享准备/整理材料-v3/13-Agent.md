# 13. Agent：从生成答案到完成任务

## 0. 本章位置

最后一章。模型层面已经完整（结构、训练、生成、优化），但 LLM 天然不具备：访问实时数据、执行外部操作、长期保存状态、保证任务按步骤完成、验证最终结果。本章讲模型外部的系统如何补上这些能力。

本章的核心是区分**模型**和**系统**。

---

# 1. LLM 的能力边界

## 问题

LLM 的基础运行方式：

```text
接收上下文
→ 预测下一个 Token
→ 持续生成
```

它天然做不到（不管参数多大）：

| 缺失 | 原因 |
|---|---|
| 访问实时数据 | 训练数据有时间截止点 |
| 执行外部操作 | 它只能输出文本 |
| 长期保存状态 | Inference 不更新参数 |
| 保证多步任务完成 | 一次生成无执行反馈 |
| 验证结果 | 输出概率分布，不验证事实 |

## 核心本质

**LLM 是"生成器"，不是"执行器"——缺的不是智能，是与世界的接口。**

---

# 2. Streaming（快速定位）

**改变什么**：把已生成的 Token 逐步返回给用户，降低等待感。

**不改变什么**：模型仍按 Token 顺序生成；不提升模型能力，只改变交互形式。

**定位**：LLM 应用工程的起点，不是 Agent 的核心能力。

---

# 3. Tool Call（工具调用）

## 解决的问题

让模型能"使用"它没有的能力（查库、搜索、发邮件）。

## 定义

**Tool Call 是模型输出结构化调用请求（工具名 + 参数）、由外部系统真正执行的机制。**

## 核心机制

完整闭环：

```text
用户提出任务
→ 模型判断需要工具
→ 输出结构化工具参数（JSON）
→ 系统执行工具
→ 结果返回模型（拼回上下文）
→ 模型继续回答
```

例：

```json
{
  "tool": "query_metrics",
  "arguments": { "service": "order-api", "window": "30m" }
}
```

**关键结论：模型不直接执行工具。**它负责决定调用什么、生成参数；外部系统负责真正执行。模型输出的只是一个请求。

## 核心本质

**模型出"调用请求"，系统出"执行"——生成能力借此接入真实世界。**

---

# 4. ReAct

## 解决的问题

一次性生成无法根据执行结果修正——错了就一路错到底。

## 定义

**ReAct 是"推理（Reasoning）与行动（Acting）交替"的模式：观察 → 推理 → 行动 → 新观察 → 继续推理的循环。**

## 核心机制

```text
观察当前状态
→ 推理下一步（Thought：我还需要什么信息）
→ 执行动作（Action：调用工具）
→ 获得新结果（Observation）
→ 再次推理
→ ……直到得出最终回答
```

与普通多轮对话的区别：多轮对话的驱动力是**用户**的追问；ReAct 循环的驱动力是**环境反馈**，模型在单次任务内自我推进。

## 核心本质

**把一次性生成，变成基于环境反馈不断修正的循环。**

---

# 5. 规划（Planning）

## 解决的问题

复杂目标无法一步完成，直接边做边想容易迷失或遗漏。

## 定义

**规划是把复杂目标拆成有序子任务、并管理其执行与调整的过程。**

## 核心机制

```text
明确目标
→ 制定计划（拆子任务、定顺序）
→ 逐步执行
→ 检查中间结果
→ 必要时调整计划
```

两种模式（不是二选一）：

- **边想边做**：每步根据当前状态决定下一步（ReAct 风格）；
- **先计划再执行**：先产出完整计划，再按计划走。

**规划器和执行器可以由同一个模型或不同模型承担。**

## 核心本质

**用"先拆解、再执行、可调整"替代"一口气做完"。**

---

# 6. Skill（技能）

## 解决的问题

Agent 每次都从零临时推理，容易不稳定：同类任务重复犯同样的错。

## 定义

**Skill 是针对某类任务封装的可复用执行知识：步骤、约束、工具用法、输入输出规范、异常处理。**

## 核心机制

例："发布周报"的 Skill 可能包含——数据从哪查、格式模板、发给谁、什么情况要人工确认。

### Skill 不是什么

- 不是单纯的提示词（提示词只是它的一部分载体）；
- 不是外部工具本身（工具是它调用的对象）；
- 不是完整的 Agent（Skill 不含执行循环）；
- 不是模型内部新增能力（模型参数没变）。

## 核心本质

**把"怎么做这类任务"固化成可复用的知识，替代每次临场发挥。**

---

# 7. MCP（Model Context Protocol）

## 解决的问题

每个应用 × 每个工具都要单独写一遍对接——M×N 的集成问题。

## 定义

**MCP 是统一模型系统与外部工具、数据源之间连接方式的标准协议。**

## 核心机制

MCP Server 向 Client 暴露标准化的能力（Tools、Resources、Prompts）；Host/Client 负责连接、权限和上下文组织。换了模型或换了工具，协议不变。

## 四个概念的区分（易混，一张表收尾）

| 概念 | 职责 |
|---|---|
| Tool | 提供一个具体外部能力 |
| Tool Call | 模型请求调用工具的机制 |
| MCP | 暴露和连接工具的标准协议 |
| Skill | 使用工具完成某类任务的方法 |
| Agent | 组织目标、模型、状态、工具和执行循环的系统 |

**MCP 不负责制定计划，也不等于 Agent**——协议让工具更容易被发现和调用，可靠执行仍需权限控制、错误处理和用户确认。

## 核心本质

**把"模型怎么连工具"从逐对定制变成标准协议。**

---

# 8. Agent 与 Harness

## 定义

**Agent 是围绕目标组织 LLM、状态、工具和执行循环的系统；Harness 是包围 LLM 的运行与控制层（上下文、权限、循环、校验）。**

## 核心机制

层级图：

```text
LLM
└── 负责理解和生成（决策核心）

Agent 系统 / Harness
├── 状态维护
├── 执行循环
├── 规划
├── 工具调用（真正执行）
└── 结果校验

能力封装
├── Skill
└── 工作流

连接协议
└── MCP
```

Agent 的能力来自多个部分：LLM 提供理解和决策，工具提供外部能力，Harness 提供控制循环，Skill/工作流提供稳定任务知识。

## 关键结论

**Agent 不是新的基础模型架构。**它没有改变 LLM 预测 Token 的底层机制，而是在 LLM 外部加入目标、状态、工具、反馈和控制流程。看到一个 AI 产品"能完成任务"时，要判断：**这是模型本身的新能力，还是模型 + 工具 + 控制系统的系统能力？**

## 核心本质

**模型负责决定，系统负责执行——Agent = LLM + 目标 + 状态 + 工具 + 循环。**

---

# 9. 极简总结

**Tool Call = 模型出请求、系统出执行；ReAct = 环境反馈驱动的推理-行动循环；规划 = 拆解-执行-调整；Skill = 固化的任务知识；MCP = 连接工具的标准协议；Agent = 把模型组织进执行循环的系统，不是新模型。**

---

# 10. 收尾

回到整套分享的主线，每一步"交给机器的内容"：

| 阶段 | 交给机器的内容 |
|---|---|
| 传统机器学习 | 从数据中寻找参数 |
| 深度学习 | 自动学习特征 |
| Transformer | 自动建立上下文关系 |
| GPT | 从海量文本中学习通用语言能力 |
| 现代 LLM | 按指令迁移能力并进行复杂推理 |
| Agent | 根据目标选择行动并使用外部工具 |

再压缩一层：

```text
规则自动化
→ 参数自动化
→ 特征自动化
→ 表示自动化
→ 任务适配自动化
→ 行动自动化
```

面对新 AI 概念时的五个判断问题：

1. 它改变的是模型结构、训练方式、Inference，还是模型外部系统？
2. 它使用了什么数据或反馈信号？
3. 它实际优化的目标是什么？
4. 能力来自模型参数，还是工具、上下文和工作流？
5. 它在哪些条件下有效，又不能保证什么？
