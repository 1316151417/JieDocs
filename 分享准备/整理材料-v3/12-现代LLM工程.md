# 12. 现代 LLM 工程：做大、做长、做快

## 0. 本章位置

上一章遗留三个工程问题：长上下文的成本、大模型的算力、部署的显存与延迟。本章按"解决什么问题"定位现代 LLM 的常用工程组件。

本章的原则：**只明确每个组件"位于哪里、解决什么问题"，不展开实现细节。**这些组件会不断迭代，但它们回应的问题稳定。

---

# 1. 架构组件（现代 Decoder Block 的常见选择）

## 1.1 RMSNorm

**解决的问题**：深层网络训练时数值不稳定。

**核心机制**：比原始 LayerNorm 更简化的归一化（只用均方根缩放，不减均值、不加偏置），计算更少。

**核心本质**：**更轻量的"稳压器"，让深层堆叠训得动。**

## 1.2 RoPE 旋转位置编码

**解决的问题**：把位置信息加入 Attention（第 6 章已定位）。

**核心机制**：对 Q、K 做位置相关的旋转，使 Q·K 的匹配分数只依赖**相对位置**；外推到更长上下文的性质优于绝对编码。

**核心本质**：**让内容匹配天然感知相对距离。**

## 1.3 SwiGLU

**解决的问题**：FFN 的表达能力与效率。

**核心机制**：带门控的激活结构（两路线性变换，一路过激活充当"门"控制另一路），现代 FFN 的常见选择。

**核心本质**：**给逐位置加工（FFN）加上"开关"，增强表达。**

## 1.4 GQA（分组查询注意力）

**解决的问题**：多头注意力每个头都要存自己的 K/V，KV Cache 显存随头数线性膨胀（第 11 章伏笔）。

**核心机制**：多组 Q 共享较少的 K/V 头——Query 头保持数量，K/V 头分组共享。

```text
MHA：32 个 Q 头，32 组 KV（缓存最大）
MQA：32 个 Q 头，1 组 KV（缓存最小，质量可能下降）
GQA：32 个 Q 头，8 组 KV（折中）
```

**核心本质**：**用共享 KV 头换更小的缓存，质量与成本的折中。**

---

# 2. 注意力计算效率

## 2.1 FlashAttention

**解决的问题**：标准注意力的中间矩阵（n×n 的注意力分数）要在显存里读写，带宽成为瓶颈。

**核心机制**：不存完整 n×n 矩阵，分块计算、在高速缓存中完成——**减少显存读写，而不是减少计算量**。

**核心本质**：**让相同的数学，走更省带宽的路。**

## 2.2 长上下文的代价（定位性总结)

| 随上下文长度 n 增长 | 项目 |
|---|---|
| O(n²) | 注意力计算量 |
| 线性 | KV Cache 显存 |
| 下降 | 信息利用的可靠性（"放得进"≠"用得好"） |

---

# 3. MoE（混合专家）

**解决的问题**：想增大模型容量，但不想每次推理都激活全部参数。

**核心机制**：

```text
FFN 层替换为多个"专家" FFN
→ 路由器（Gate）为每个 Token 选择少数几个专家
→ 只有被选中的专家计算
```

参数总量可以做得很大（容量），但每个 Token 只激活一小部分（计算量）——**容量与算力解耦**。

代价：全部参数都要装进显存（省算力不省显存）；路由和负载均衡训练复杂。

**核心本质**：**容量做大，计算做小：每个 Token 只看少数"专家"。**

---

# 4. 量化

**解决的问题**：部署时显存和带宽的限制。

**核心机制**：把参数从高精度（如 FP16，每参数 2 字节）压到低精度（INT8 / INT4），显存占用和访存带宽成比例下降；代价是精度损失（现代量化方法努力把损失控制到很小）。

**核心本质**：**用更少的比特存同样的参数，换部署成本。**

---

# 5. 训练侧工程（一句话定位）

| 组件 | 解决的问题 | 一句话 |
|---|---|---|
| 混合精度训练 | 算力和显存 | 部分计算用低精度，关键路径保高精度 |
| 分布式训练 | 单卡放不下 | 数据/张量/流水线并行，多卡协同 |
| 稳定性措施 | 大模型训练发散 | 损失尖峰处理、梯度裁剪、学习率策略 |

这些属于"怎么把大模型训起来"的工程，与"模型为什么有能力"是不同层面的问题。

---

# 6. 极简总结

**RMSNorm 稳压、RoPE 给相对位置、SwiGLU 强表达、GQA 缩缓存、FlashAttention 省带宽、MoE 容量与算力解耦、量化省比特——全部围绕"做大、做长、做快"三个字。**

---

# 7. 遗留的问题

至此，"模型"这个层面讲完了：结构、训练、生成、优化。但模型本身仍然只做一件事：

```text
接收上下文 → 输出文本（或结构化 Token）
```

用户说"查询线上指标、定位异常、创建工单并通知负责人"——模型可以生成查询语句和邮件内容，但它不会真的去查监控、发邮件、检查结果。

问题从"模型应该生成什么"变成"**系统下一步应该做什么**"。
