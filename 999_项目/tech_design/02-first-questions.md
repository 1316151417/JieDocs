# 文档首先要回答什么问题？

### 一、问题定义

技术设计文档首先要回答的不是“怎么实现”，而是：我们到底要解决什么问题？

更完整一点，它首先要回答：

```text
1. 现在的问题是什么？
2. 为什么这个问题值得解决？
3. 成功之后应该变成什么样？
4. 哪些事情不在本次范围内？
5. 如果不解决，会有什么后果？
```

如果问题定义错了，后面写得越详细，偏得越远。

### 二、问题产生原因

真实项目里，团队一开始拿到的通常不是“问题”，而是“需求表达”。

例如：

```text
我们需要做一个通知系统。
我们需要优化订单查询。
我们需要支持多租户。
我们需要把这个服务拆出来。
```

这些话看起来像问题，但其实更像是某种方案、愿望或现象。真正的问题可能是：

```text
为什么现有通知能力不够？
订单查询慢到什么程度？
多租户是为了解决隔离、计费、权限，还是客户定制？
拆服务是因为团队协作问题、部署问题，还是性能问题？
```

核心矛盾是：

```text
技术实现需要确定性，但早期需求往往是模糊的。
```

### 三、解决思路

技术设计文档开头的核心思想是：先定义判断标准，再讨论解决方案。

在讨论“怎么做”之前，先让所有人知道：

```text
我们为什么做？
我们解决的是哪个具体问题？
什么叫解决成功？
什么不算本次要解决的问题？
```

### 四、方案框架

```text
问题
↓
团队容易直接从需求跳到方案，导致目标不清、边界不清、判断标准不清

核心思想
↓
在设计方案之前，先把问题、价值、目标、边界和成功标准讲清楚

关键机制
↓
说明现状有什么问题
解释为什么现在必须解决
定义本次要达到的目标
明确哪些事情不做
给出可验证的成功标准

最终效果
↓
让团队先对“为什么做”和“做到什么程度”形成共识，再进入技术方案设计
```

### 五、与其它方案比较

先写架构图不合适，因为架构图回答的是“系统怎么组织”，但如果问题没定义清楚，就不知道这个架构是在为哪个目标服务。

先写接口设计不合适，因为接口设计已经是实现层选择，太早进入接口会掩盖目标和边界的分歧。

先写技术选型不合适，因为技术选型必须依赖问题。没有问题定义，选型容易变成偏好之争。
