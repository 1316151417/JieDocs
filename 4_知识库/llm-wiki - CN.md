## LLM 维基（LLM Wiki）

一种使用 LLM 构建个人知识库的模式。

这是一份"理念文件"（idea file），设计初衷是被复制粘贴到你自己的 LLM Agent 中（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达高层理念，而具体的细节则由你的 agent 在与你的协作中逐步构建出来。

## 核心思想

大多数人对 LLM 和文档的体验类似 RAG：你上传一批文件，LLM 在查询时检索相关片段，然后生成答案。这行得通，但 LLM 每次都要从头重新发现知识。没有积累。问一个需要综合五份文档才能回答的微妙问题，LLM 每次都得重新找到并拼凑相关片段。什么都没有沉淀下来。NotebookLM、ChatGPT 文件上传，以及大多数 RAG 系统都是这样工作的。

这里的理念不同。LLM 不是在查询时才从原始文档中检索，而是**增量地构建并维护一个持久的维基**——一个结构化、相互链接的 Markdown 文件集合，介于你与原始来源之间。当你添加一个新来源时，LLM 不只是为日后检索建立索引。它会阅读、提取关键信息，并把它整合进现有维基——更新实体页面、修订主题摘要、标注新数据与旧论断相矛盾之处、强化或质疑不断演进的综述。知识被编译一次，然后*保持最新*，而不是在每次查询时重新推导。

这就是关键区别：**维基是一个持久的、不断复利的产物。** 交叉引用已经就位。矛盾之处已被标记。综述已经反映了你读过的一切。维基随着你添加的每一个来源、提出的每一个问题而变得越来越丰富。

你从不（或极少）亲自撰写维基——LLM 负责编写和维护全部内容。你负责 sourcing（寻找来源）、探索，以及提出正确的问题。LLM 承担所有枯燥的工作——那些让知识库随时间真正变得有用的总结、交叉引用、归档和簿记工作。在实践中，我一边开着 LLM agent，另一边开着 Obsidian。LLM 根据我们的对话进行编辑，我则实时浏览结果——跟踪链接、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE；LLM 是程序员；维基是代码库。

这可以应用于很多不同场景。举几个例子：

- **个人**：追踪你自己的目标、健康、心理状态、自我提升——归档日记、文章、播客笔记，随时间构建出一个关于你自己的结构化图景。
- **研究**：在数周或数月内深入某个主题——阅读论文、文章、报告，并增量地构建出一个带有演进中论点的综合性维基。
- **读一本书**：边读边归档每一章，为角色、主题、情节线索以及它们之间的关联建立页面。读到最后你会得到一个丰富的伴读维基。想想像 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝维基——成千上万相互链接的页面，涵盖角色、地点、事件、语言，由一群志愿者花数年建成。你完全可以在阅读时亲自构建类似的东西，而由 LLM 完成所有交叉引用和维护。
- **商业/团队**：由 LLM 维护的内部维基，输入来源是 Slack 讨论、会议记录、项目文档、客户通话。可能有人类在回路中审查更新。维基保持最新，因为 LLM 承担了团队里没人愿意做的维护工作。
- **竞品分析、尽职调查、旅行规划、课程笔记、爱好深挖**——任何你需要随时间积累知识、并希望它被组织起来而非散落各处的场景。

## 架构

一共有三层：

**原始来源（Raw sources）**——你精选的源文档集合。文章、论文、图片、数据文件。这些是不可变的——LLM 从中读取但从不修改它们。这是你的事实来源（source of truth）。

**维基（The wiki）**——一个由 LLM 生成的 Markdown 文件目录。摘要、实体页面、概念页面、对比、概述、综述。LLM 完全拥有这一层。它创建页面，在新来源到达时更新它们，维护交叉引用，并保持一切一致。你来读；LLM 来写。

**模式文件（The schema）**——一份文档（例如 Claude Code 的 CLAUDE.md，或 Codex 的 AGENTS.md），告诉 LLM 维基如何组织、约定是什么，以及在摄入来源、回答问题或维护维基时应遵循哪些工作流。这是关键的配置文件——正是它让 LLM 成为一个有纪律的维基维护者，而不是一个通用聊天机器人。随着你摸清什么适合自己的领域，你和 LLM 会随时间共同演进这份文件。

## 操作

**摄入（Ingest）。** 你把一个新来源放进原始集合，并让 LLM 处理它。一个示例流程：LLM 阅读来源、与你讨论关键要点、在维基中写一个摘要页面、更新索引、更新维基中相关的实体和概念页面，并向日志追加一条记录。一个来源可能会触及 10–15 个维基页面。就我个人而言，我偏好一次只摄入一个来源并保持参与——我阅读摘要、检查更新、并引导 LLM 该强调什么。但你也完全可以一次性批量摄入多个来源而少加监督。找到适合自己风格的工作流，并把它记录到 schema 中供未来会话使用，这取决于你。

**查询（Query）。** 你针对维基提问。LLM 搜索相关页面、阅读它们，并综合出一个带引用的答案。答案根据问题可以采取不同形式——一个 Markdown 页面、一张对比表、一份幻灯片（Marp）、一张图表（matplotlib）、一块画布（canvas）。一个重要洞见：**好的答案可以作为新页面归档回维基。** 你请求的一次对比、一项分析、你发现的一处关联——这些都是有价值的，不应消失在聊天历史里。这样你的探索就会像摄入的来源一样，在知识库中不断复利。

**检查（Lint）。** 定期让 LLM 对维基做健康检查。寻找：页面之间的矛盾、已被更新来源取代的过时论断、没有入链的孤立页面、被提到却缺少独立页面的重要概念、缺失的交叉引用、可以通过网络搜索补全的数据空白。LLM 很擅长建议要调查的新问题和要寻找的新来源。这让维基在生长过程中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（以及你）在维基生长时导航它。它们用途不同：

**index.md** 面向内容。它是维基中所有内容的目录——每个页面列出链接、一行摘要，以及可选的元数据如日期或来源数。按类别组织（实体、概念、来源等）。LLM 在每次摄入时更新它。回答查询时，LLM 先读索引找到相关页面，再深入它们。这在中等规模（约 100 个来源、数百个页面）下效果出奇地好，并且避免了基于嵌入的 RAG 基础设施。

**log.md** 按时间顺序。它是一个只追加的记录，记下发生了什么以及何时——摄入、查询、检查（lint）。一个有用的技巧：如果每条记录以一致的prefix开头（例如 `## [2026-04-02] ingest | 文章标题`），日志就可以用简单的 unix 工具解析——`grep "^## \[" log.md | tail -5` 给你最近 5 条记录。日志为你提供维基演进的时间线，并帮助 LLM 了解最近做了什么。

## 可选：CLI 工具

到某个时候，你可能想构建一些小工具来帮助 LLM 更高效地操作维基。最显而易见的一个是针对维基页面的搜索引擎——小规模下索引文件就够了，但随着维基增长你会想要正经的搜索。[qmd](https://github.com/tobi/qmd) 是一个不错的选择：它是一个面向 Markdown 文件的本地搜索引擎，带有混合 BM25/向量搜索和 LLM 重排序，全部在设备端运行。它既有 CLI（这样 LLM 可以 shell 调用它），也有 MCP server（这样 LLM 可以把它当作原生工具使用）。你也可以自己构建更简单的东西——LLM 可以在你需要时帮你凭直觉写一个（vibe-code）朴素搜索脚本。

## 技巧与窍门

- **Obsidian Web Clipper** 是一个浏览器扩展，可将网页文章转换为 Markdown。对于快速把来源放进你的原始集合非常有用。
- **把图片下载到本地。** 在 Obsidian 设置 → 文件与链接中，把"附件文件夹路径"设为一个固定目录（例如 `raw/assets/`）。然后在设置 → 快捷键中，搜索"Download"找到"Download attachments for current file"，并把它绑定到一个快捷键（例如 Ctrl+Shift+D）。剪藏一篇文章后，按下快捷键，所有图片都会被下载到本地磁盘。这是可选的但很有用——它让 LLM 能直接查看和引用图片，而不是依赖可能失效的 URL。注意，LLM 无法一次性原生读取带内联图片的 Markdown——变通办法是让 LLM 先读文本，再单独查看部分或全部被引用的图片以获取额外上下文。这有点笨拙，但够用。
- **Obsidian 的图谱视图（graph view）** 是查看你维基形态的最佳方式——什么连着什么、哪些页面是枢纽、哪些是孤立的。
- **Marp** 是一种基于 Markdown 的幻灯片格式。Obsidian 有它的插件。便于直接从维基内容生成演示文稿。
- **Dataview** 是一个 Obsidian 插件，可对页面 frontmatter 执行查询。如果你的 LLM 给维基页面添加了 YAML frontmatter（标签、日期、来源数），Dataview 可以生成动态表格和列表。
- 维基只是一个 Markdown 文件的 git 仓库。你免费获得版本历史、分支和协作。

## 为什么这样可行

维护知识库的枯燥部分不在于阅读或思考——而在于簿记。更新交叉引用、保持摘要最新、标注新数据何时与旧论断矛盾、在数十个页面间维护一致性。人类会放弃维基，因为维护负担的增长快于价值的增长。LLM 不会厌倦，不会忘记更新某条交叉引用，并且能一次性触及 15 个文件。维基之所以保持维护良好，是因为维护成本接近于零。

人的工作是精选来源、引导分析、提出好问题、思考这一切意味着什么。LLM 的工作是其他一切。

这个理念在精神上与 Vannevar Bush 1945 年的 Memex 相通——一个个人的、精选的知识存储，文档之间有关联轨迹。Bush 的设想其实更接近这个，而不是互联网最终变成的样子：私有的、主动精选的、文档之间的关联与文档本身同样有价值。他无法解决的部分是"由谁来做维护"。LLM 解决了这一点。

## 说明

本文档有意保持抽象。它描述的是理念，而非某个具体实现。确切的目录结构、schema 约定、页面格式、工具链——所有这些都取决于你的领域、你的偏好，以及你选择的 LLM。上面提到的一切都是可选的、模块化的——挑有用的，忽略没用的。例如：你的来源可能纯文本，所以根本不需要图片处理。你的维基可能小到只需要索引文件，不需要搜索引擎。你可能不在乎幻灯片，只想要 Markdown 页面。你可能想要一套完全不同的输出格式。使用它的正确方式，是与你的 LLM agent 分享这份文档，并一起协作实例化一个适合你需求的版本。这份文档唯一的工作就是传达这个模式。剩下的你的 LLM 能自己搞定。
