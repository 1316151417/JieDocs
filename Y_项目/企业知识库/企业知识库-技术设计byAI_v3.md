# **1. 项目背景**

## **1.1 背景问题**

当前企业研发体系中，系统知识长期存在以下问题：

### **1）系统知识缺少沉淀**

系统长期演进后：

- 文档质量低
- 文档长期过期
- 历史设计无人维护
- 核心逻辑依赖资深研发经验
- 新成员理解系统成本高

知识散落在：

- 代码库
- SQL
- 配置
- 飞书
- PR
- 日志
- 事故复盘
- 人脑经验

缺少统一、长期可维护的知识结构。

---

### **2）AI 无法真正理解企业系统**

当前 AI 工程实践大多基于：

- 文档问答
- 向量检索
- 代码片段生成

但企业系统真正复杂的部分在于：

- 调用链
- 状态流
- 数据流
- 业务边界
- 上下游依赖
- 风险链路

传统 RAG 很难形成系统级认知。

导致 AI 难以进入：

- 老系统迭代
- 故障排查
- 复杂链路分析
- CR
- 风险评估

等核心研发流程。

---

## **1.2 建设目标**

建设一套：

# **基于代码库的长期知识系统**

核心目标：

- 基于代码自动生成系统 Wiki
- 建立系统级认知结构
- 支持 AI 理解复杂系统
- 支持增量更新
- 支持长期维护

---

## **1.3 核心设计原则**

### **Code First**

代码作为最高可信知识源。

文档作为辅助解释信息。

---

### **Local First**

代码分析优先依赖本地环境。

避免复杂中心化编译环境。

---

### **Incremental Update**

基于 Git Diff 增量更新。

避免全量重建。

---

### **Domain Oriented**

按业务域组织知识。

而非按代码目录组织。

---

# **2. 系统目标**

## **2.1 第一阶段目标（V1）**

V1 聚焦：

# **跑通系统认知闭环**

核心能力：

|**能力**|**目标**|
|---|---|
|代码结构分析|理解系统结构|
|调用链分析|理解上下游|
|Agent 探索|建立系统认知|
|Wiki 自动生成|形成长期知识|
|增量更新|长期维护|

---

## **2.2 V1 不建设内容**

以下能力暂不建设：

- GraphRAG
- 图数据库
- Runtime 全链路分析
- 多 Agent 协同
- 在线 AI 搜索平台

原因：

当前阶段优先验证：

# **AI 是否能够稳定理解系统**

---

# **3. 总体架构**

## **3.1 架构模式**

采用：

# **Local-first + Remote Enhancement**

架构。

---

## **3.2 总体架构图**

```text
Local Repository
        ↓
CodeGraph
        ↓
React Agent
        ↓
Markdown Wiki
        ↓
Git / Feishu
```

远程服务仅负责公共能力：

```text
LLM Gateway
MCP Tool
Webhook

权限控制
```

# **4. 核心模块设计**

# **4.1 CodeGraph Layer**

## **职责**

负责代码结构分析与导航。

提供：

- AST
- Symbol
- 调用链
- SQL 引用
- Service 依赖
- MQ 依赖
- RPC 依赖

---

## **核心目标**

帮助 Agent：

# **快速理解系统结构**

避免：

- 全仓 grep
- 重复扫描
- 上下文爆炸

---

## **技术方案**

V1 不自研 Graph Engine。

直接复用现有能力：

- codegraph
- tree-sitter
- language server

---

## **输出示例**

```json
{
  "service": "RefundService",
  "calls": [
    "PaymentClient"
  ],
  "db": [
    "refund_order"
  ],
  "mq": [
    "refund_topic"
  ]
}
```

---

## **设计原则**

### **不修改 CodeGraph 内核**

原因：

- 降低维护成本
- 避免 Fork
- 避免多语言适配复杂度失控

系统仅基于 CodeGraph 输出进行增强。

---

# **4.2 Agent Layer**

## **职责**

基于 CodeGraph 建立系统认知。

输出 Wiki 内容。

---

## **Agent 目标**

Agent 不负责逐文件总结。

重点分析：

- 系统职责
- 业务边界
- 核心链路
- 数据模型
- 状态流
- 上下游依赖
- 风险点

---

## **Agent 输入**

包括：

- CodeGraph 结果
- AST 信息
- SQL
- 配置
- 外部文档

---

## **Agent 输出**

直接生成 Markdown Wiki。

---

## **探索模式**

采用：

# **React Agent**

多轮探索模式。

典型流程：

```text
定位入口
    ↓
分析调用链
    ↓
分析状态流
    ↓
分析数据模型
    ↓
生成系统认知
```

---

## **Prompt 设计**

Prompt 聚焦：

- 系统职责
- 业务边界
- 核心状态流
- 风险链路

避免：

- 逐文件解释
- 代码翻译型输出

---

## **上下文控制**

避免一次性加载全仓代码。

采用：

- Symbol 定位
- 调用链导航
- Domain 分区
- 分层探索

控制上下文规模。

---

# **4.3 Wiki Layer**

## **职责**

负责：

- Markdown 管理
- 目录组织
- 索引生成
- Git 持久化
- 飞书同步

不负责系统分析。

---

## **文档格式**

V1 采用：

- Markdown
- Git

原因：

- 易维护
- 易 Diff
- 易增量更新
- 易集成静态站点

---

## **推荐技术栈**

|**类型**|**技术**|
|---|---|
|文档格式|Markdown|
|文档站点|Docusaurus / MkDocs|
|存储|Git|

---

# **5. Wiki 组织设计**

# **5.1 组织原则**

按业务域组织。

不按代码目录组织。

---

## **推荐结构**

```text
wiki/
├── order/
├── payment/
├── refund/
├── settlement/
└── common/
```

---

# **5.2 单篇 Wiki 结构**

推荐结构：

---

## **1）系统职责**

说明模块核心功能。

---

## **2）业务边界**

说明：

- 负责内容
- 不负责内容

---

## **3）核心链路**

例如：

```text
退款申请
→ 风控校验
→ 支付退款
→ 状态更新
→ MQ通知
```

---

## **4）数据模型**

包括：

- 核心表
- 生命周期
- 状态

---

## **5）状态流**

描述状态变化过程。

---

## **6）依赖关系**

包括：

- RPC
- MQ
- Redis
- DB

---

## **7）风险点**

包括：

- 幂等
- 一致性
- 补偿
- 延迟

---

## **8）历史演进**

记录：

- 历史设计
- 兼容逻辑
- 演进原因

---

# **6. 增量更新设计**

## **6.1 目标**

避免全量重建。

降低长期维护成本。

---

## **6.2 更新流程**

```text
Git Diff
    ↓
CodeGraph 更新
    ↓
影响分析
    ↓
Agent 重新探索
    ↓
更新对应 Wiki
```

---

## **6.3 更新粒度**

采用：

# **Node-based Update**

仅更新受影响模块。

---

## **6.4 影响分析维度**

包括：

- Symbol 变化
- 调用链变化
- SQL 变化
- 配置变化

---

# **7. 外部文档设计**

## **7.1 外部文档角色**

外部文档作为辅助知识源。

包括：

- RFC
- 技术方案
- PRD
- 事故复盘
- 排查手册

---

## **7.2 使用原则**

外部文档：

# **不覆盖代码分析结果**

仅用于补充：

- 设计背景
- 业务规则
- 风险说明
- 历史原因

---

## **7.3 挂载方式**

外部文档挂载到对应业务节点：

例如：

```text
RefundService
├── Code Analysis
├── SQL
├── RFC
├── Incident
└── PRD
```

---

# **8. 远程增强能力**

远程服务仅提供公共能力。

不承担代码解析职责。

# **8.2 MCP Tool Service**

统一封装：

- CodeGraph
- Git
- SQL Tool

---

# **8.3 Feishu Integration**

负责：

- 文档同步
- 权限控制
- 自动发布

---

# **8.4 Webhook**

支持：

- Git Push 自动更新
- 定时增量更新

# **10. 风险与限制**

|**风险**|**说明**|
|---|---|
|多语言复杂度|不同语言解析能力不同|
|大仓库上下文|Agent 容易上下文爆炸|
|文档可信度|外部文档可能过期|
|Domain 划分困难|业务边界可能不清晰|
|Agent 稳定性|输出质量存在波动|

---

# **11. 最终目标**

构建一套：

# **面向 AI 的系统认知基础设施**

实现：

- 企业知识长期沉淀
- AI 理解复杂系统
- 系统认知长期演化
- 支撑 AI 进入研发核心流程
