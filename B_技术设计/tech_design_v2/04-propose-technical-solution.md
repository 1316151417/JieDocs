# 如何提出技术方案？

### 一、问题定义

提出技术方案要解决的问题是：如何把一个模糊的解决想法，表达成团队可以理解、评审、实现和验证的工程方案。

它至少要回答：

```text
这个方案如何解决前面定义的问题？
系统会变成什么结构？
核心流程会如何变化？
关键数据如何流动？
模块之间如何协作？
失败时怎么办？
为什么这个方案在当前约束下可行？
```

### 二、问题产生原因

从“知道问题”到“能落地解决问题”之间，有很长一段距离。

常见的错误是直接写结论：

```text
使用 Redis 缓存热点数据。
引入 MQ 解耦订单流程。
将用户模块拆成独立服务。
新增一张聚合表提升查询性能。
```

这些表达只说了“用什么”，没有说“如何解决问题”。

核心矛盾是：

```text
技术方案需要足够具体，才能指导实现；但又不能一开始陷入代码细节，否则会失去架构判断。
```

### 三、解决思路

提出技术方案的核心思想是：从问题出发，说明系统将通过哪些关键机制发生变化，从而达到目标。

好的技术方案通常遵循：

```text
先给整体思路
再说明系统结构
再说明关键流程
再说明数据变化
再说明边界与异常
最后说明方案为什么有效
```

### 四、方案框架

```text
问题
↓
团队知道要解决什么，但如果只写技术选型或实现细节，无法判断方案是否真的有效

核心思想
↓
用“整体结构 + 关键机制 + 关键流程 + 数据变化 + 异常处理”来说明问题如何被解决

关键机制
↓
先用一段话说明方案总览
画出新旧系统的关键差异
说明核心模块及职责
说明主要流程如何运转
说明数据如何产生、存储、流转和消费
说明接口边界与依赖关系
说明失败、重试、降级、回滚等异常路径
说明方案如何满足目标与约束

最终效果
↓
让评审者能判断方案是否合理，让实现者知道如何落地，让未来维护者理解系统为什么这样设计
```

### 五、与其它方案比较

只写技术选型不够，因为技术选型只是工具选择。

只画架构图不够，因为架构图能表达结构，但不能完整表达行为。

直接写实现细节不合适，因为实现细节会让文档过早变重，也容易把评审焦点带偏。

只描述最终状态不够，因为最终状态不能说明“怎么从当前系统走过去”。
