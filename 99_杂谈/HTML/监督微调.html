01 — FIRST PRINCIPLES

第一性原理拆解

在建造任何建筑之前，建筑师必须理解材料的物理属性、力的传递路径、以及人与空间的关系。 同理，在实施 SFT 之前，我们必须回到最基础的问题：什么是微调？为什么需要它？它的本质机制是什么？

⬡
本源问题一
为什么预训练不够？

预训练模型通过自回归/掩码语言建模习得了语言的统计规律和世界知识，但它学到的是一个"万能补全器"—— 它不知道用户在提问时期待什么样的回答格式、风格和行为模式。 预训练目标（next token prediction）和下游任务目标（instruction following）之间存在根本性的目标函数鸿沟。

◈
本源问题二
微调的本质是什么？

从信息论视角，微调是在模型已有的先验分布 P(x) 上施加条件约束，将其转换为条件分布 P(y|x, task)。 这不是"教会模型新知识"，而是激活和组织模型已有的能力， 让它在特定任务的流形上表现出一致的行为模式。 参数更新的幅度虽小，但改变了模型在概率空间中的决策边界。

△
本源问题三
监督信号为什么关键？

监督微调的核心假设是：高质量的输入-输出对可以定义"正确行为"。 模型通过最小化与目标输出之间的差异来调整内部表征。 但监督信号的质量上限决定了模型性能的上限——垃圾进，垃圾出，这是不可逾越的信息论边界。

◇
本源问题四
参数空间如何选择？

全参数微调 vs 参数高效微调（PEFT）的本质权衡： 在高维参数空间中，任务相关的有效子空间远小于全参数空间。 LoRA 假设权重更新具有低秩结构，Adapter 在层间插入瓶颈模块， Prefix-Tuning 在注意力空间中添加可控维度。 选择哪种方式，取决于任务复杂度与计算预算的帕累托最优。

Step 01 — 数据准备：地基决定高度

数据是 SFT 的地基。数据质量的上限决定了模型性能的不可突破上限。建筑师知道，再精美的设计也无法弥补劣质地基。

  • 数据来源规划：确定数据采集渠道——人工标注、现有数据集、模型生成（Self-Instruct）、用户日志筛选
  • 质量控制体系：建立多轮审查流程，包含自动过滤（长度、重复度、毒性检测）和人工抽检
  • 多样性保障：任务类型覆盖、难度梯度分布、语言/领域平衡——避免模型过拟合到特定模式
  • 标注规范设计：编写详细的标注指南，包含正例/反例，确保标注者间一致性（Cohen's Kappa > 0.8）
  • 规模评估：一般经验，SFT 数据在 1K-100K 条高质量样本即可显著改变模型行为模式

Step 02 — 数据预处理：将原材料加工为结构体

原始数据必须转化为模型可以理解的结构化格式。这一步的质量直接影响训练效率和最终效果。

  • 模板化：将 instruction-input-output 映射为统一的对话模板（ChatML, Alpaca, ShareGPT 格式）
  • Tokenization：选择合适的 tokenizer，确认特殊 token 的映射，处理多语言场景
  • 长度管理：设定 max_length（常见 2048/4096），对过长样本进行截断或分割
  • Loss Masking：仅对 assistant 回复部分计算 loss，避免模型学习复读用户指令
  • 数据去重：基于 MinHash/SimHash 去除近似重复样本，防止记忆化

Step 03 — 模型选择：选择合适的结构材料

基础模型的选择决定了微调的起点和天花板。不同架构有不同的微调特性。

  • 模型规模：7B 适合快速迭代和资源受限场景；13B-70B 在复杂任务上表现更佳
  • 架构选择：Decoder-only（GPT/Llama系列）是当前主流，擅长生成；Encoder-Decoder（T5）在某些特定任务上仍有优势
  • 基础能力评估：在候选模型上运行基准测试，评估预训练阶段的知识覆盖度
  • 微调方法选择：全参数微调 vs LoRA vs QLoRA——依据资源和任务复杂度做出帕累托最优决策
  • License 检查：确认模型的商用许可（Llama 2 社区许可、Mistral Apache 2.0 等）

Step 04 — 训练配置：精密调控施工参数

训练超参数的调整如同调整建筑施工中的每一个螺栓——偏差看似微小，但累积效应可能致命。

  • 学习率：典型范围 1e-5 ~ 5e-5，配合 cosine decay 或 linear warmup（通常 3-10% 步数）
  • Batch Size：通过梯度累积实现有效大批量（128-256），注意 batch size 与学习率的线性缩放关系
  • 训练轮次：通常 1-3 epochs，过多会导致过拟合和灾难性遗忘
  • 正则化：Weight decay (0.01-0.1)、Dropout（谨慎使用）、梯度裁剪 (max_grad_norm=1.0)
  • 混合精度：BF16/FP16 训练节省显存，注意 loss scaling 策略
  • DeepSpeed/FSDP：多卡并行策略选择——ZeRO Stage 2/3 和全切片数据并行

Step 05 — 评估验证：质量检测与验收

建筑需要安全检测，模型需要系统性评估。单一指标无法反映模型的真实能力。

  • 自动评估：在标准基准上测试（MMLU、HumanEval、GSM8K 等），建立量化基线
  • 人工评估：通过 A/B 测试、Likert 评分评估回答质量——流畅性、准确性、有用性、安全性
  • LLM-as-Judge：使用 GPT-4 等强模型作为评审，批量评估回答质量（成本效益高但需校准）
  • 安全性测试：红队测试（Red Teaming）——系统性地尝试攻击模型，评估有害输出风险
  • 回归测试：确保微调没有损害模型在通用任务上的表现（能力保持度检查）

Step 06 — 部署迭代：持续维护与改进

建筑交付后需要持续维护，模型部署后同样需要监控和迭代升级。

  • 模型压缩：量化（GPTQ/AWQ/GGUF）减少推理成本，蒸馏到更小模型部署
  • 推理优化：vLLM/TGI 部署，启用 KV-Cache、Continuous Batching、PagedAttention
  • 监控体系：跟踪线上指标——延迟、吞吐量、用户满意度、异常输出率
  • 数据飞轮：收集用户反馈 → 筛选高质量样本 → 进入下一轮 SFT 迭代
  • 对齐增强：SFT 后通常接 RLHF/DPO 进一步对齐人类偏好
sft_training.py — 典型 SFT 训练代码框架 
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import SFTTrainer, SFTConfig
from peft import LoraConfig, get_peft_model

# Step 1: 加载基座模型
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3-8B",
    torch_dtype="bfloat16",
    device_map="auto",
)
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3-8B")

# Step 2: 配置 LoRA（参数高效微调）
lora_config = LoraConfig(
    r=16,                   # 秩，控制适配器容量
    lora_alpha=32,           # 缩放因子
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)

# Step 3: 训练配置
training_config = SFTConfig(
    output_dir="./sft_output",
    num_train_epochs=3,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,  # 有效 batch = 4 * 8 = 32
    learning_rate=2e-5,
    lr_scheduler_type="cosine",
    warmup_ratio=0.05,
    bf16=True,
    max_seq_length=2048,
    logging_steps=10,
    save_strategy="epoch",
)

# Step 4: 启动训练
trainer = SFTTrainer(
    model=model,
    args=training_config,
    train_dataset=train_dataset,  # 已预处理的指令数据集
    tokenizer=tokenizer,
)
trainer.train()

04 — CASE STUDIES

典型案例研究

从实践中学习，三个不同维度的真实 SFT 案例， 展示第一性原理在不同场景中的应用。

Code Generation
案例一：代码生成能力的 SFT 增强

挑战：基础模型虽然具备代码知识，但生成的代码往往缺乏可执行性、不符合最佳实践、缺少注释和类型标注。

第一性原理分析：代码生成的本质是将自然语言意图映射到形式化语言。关键约束包括：语法正确性（可编译）、语义正确性（可运行）、风格一致性（可维护）。

SFT 策略： ① 数据构建：收集高质量的 (需求描述, 可执行代码) 对，来源包括 GitHub 高星项目、LeetCode 高赞解答、Stack Overflow 排名答案； ② 数据格式：不仅包含最终代码，还包含思考过程（chain-of-thought）、复杂度分析、边界条件说明； ③ 训练技巧：在 loss 计算时对代码块内的 token 给予更高权重，强化模型对代码格式的精确学习。

结果：经过 SFT 后，模型在 HumanEval 上 pass@1 从基座的 30% 提升至 65%， 代码的可执行率和可读性均有显著提升。关键洞见：数据质量比数量更重要——5K 条高质量代码对的效果优于 50K 条低质量样本。

Domain Expert
案例二：医疗垂直领域的专业对话

挑战：通用模型在医疗场景中存在幻觉风险、术语使用不准确、缺乏循证医学思维，直接应用可能造成严重后果。

第一性原理分析：医疗对话的特殊性在于：① 错误的代价极高（涉及生命安全）；② 专业术语的精确性要求极高；③ 需要模型表达不确定性而非自信地给出错误答案。

SFT 策略： ① 数据由执业医师标注和审核，确保医学准确性； ② 在训练数据中系统性地包含"我不确定"/"建议咨询专业医生"的样本，教会模型表达不确定性； ③ 引入结构化输出格式：症状分析 → 可能诊断 → 建议检查 → 注意事项； ④ Safety alignment：在 SFT 中嵌入拒绝有害请求的样本。

结果：模型在医学问答准确率提升 40% 的同时，幻觉率降低 60%。 更重要的是，模型学会了在超出能力范围时主动提示用户寻求专业医疗帮助。 关键洞见：教模型"知道不知道什么"比教它"知道什么"更重要。

Multi-Turn
案例三：复杂多轮指令遵循能力构建

挑战：模型在单轮任务上表现良好，但在多轮对话中容易丢失上下文、忘记约束条件、无法处理指令修正。

第一性原理分析：多轮指令遵循的核心困难是长期依赖管理。模型需要：① 在注意力窗口内维护所有约束条件的表征；② 区分新指令是"补充"还是"替换"之前的约束；③ 在每一步都保持全局一致性。

SFT 策略： ① 构建复杂的多轮数据，包含指令修正、追加约束、否定指令等场景； ② 在训练中将完整对话作为一个样本，而非拆分为独立轮次； ③ 在数据中嵌入"回顾"类回答——让模型在回答前复述当前所有有效约束； ④ 课程学习策略：从 2 轮对话开始，逐步增加到 10+ 轮。

结果：多轮指令遵循准确率从 45% 提升至 78%，约束保持率（Constraint Persistence Rate）从 52% 提升至 85%。 关键洞见：多轮能力不能通过单轮数据增强获得——必须在多轮环境中训练。

05 — PITFALLS & SOLUTIONS

常见陷阱与解决方案

建筑师的职责不仅是设计美观的结构，更要预见和规避潜在的风险。 以下是 SFT 实践中最常见的失败模式及其系统性解决方案。

陷阱 #1
灾难性遗忘

微调后模型在目标任务上提升了，但在通用能力上严重退化。 例如：SFT 后模型在医疗问答上变好了，但基础推理和编程能力大幅下降。

解决方案

① 使用低学习率 + 少量 epoch 控制偏离幅度； ② 在 SFT 数据中混入 5-10% 的通用指令数据（数据混合法）； ③ 采用 LoRA 等参数高效方法，保持原始权重冻结； ④ 定期在通用基准上执行回归测试。

陷阱 #2
过拟合与记忆化

模型逐字记忆训练数据中的回答，丧失泛化能力。 在生成时重复训练集中的特定短语和模式，对新输入表现不稳定。

解决方案

① 增加训练数据的多样性和规模（如果可能）； ② 使用 dropout（0.05-0.1）和 weight decay（0.01-0.1）； ③ 监控 train/eval loss 曲线，eval loss 上升时及时停止（early stopping）； ④ 限制训练 epoch 在 1-3 轮。

陷阱 #3
格式坍缩（Format Collapse）

模型开始对所有输入都输出相同的格式/模板，丧失了根据内容调整输出形式的灵活性。 表现为所有回答都以相同句式开头、使用相同的结构。

解决方案

① 确保训练数据中同一任务有多种不同的回答格式和风格； ② 避免数据中存在过强的格式偏差（如每条数据都以"好的，我来..."开头）； ③ 在数据预处理阶段统计格式多样性指标，确保覆盖短/长、结构化/自由文本等多种形式。

陷阱 #4
学习率灾难

学习率过高导致训练不稳定甚至发散；学习率过低导致训练不充分或陷入局部最优。 常见表现：loss 震荡不降或 loss 始终保持在高位。

解决方案

① 使用 learning rate finder：从极小值开始指数增长，找到 loss 快速下降的拐点； ② 全参微调建议 1e-5 ~ 5e-5，LoRA 可使用稍高的 1e-4 ~ 3e-4； ③ 配合 cosine decay + linear warmup（3-10% 总步数）； ④ 训练初期密切监控 loss 曲线，前 100 步即可判断学习率是否合适。

微调方法 可训练参数 显存需求 训练速度 适用场景
Full Fine-Tuning 100% 极高（≥80GB × 8） 最慢 大规模数据，追求极致性能
LoRA 0.1% ~ 1% 中等（24-40GB） 快 2-3x 最通用的 PEFT 方案
QLoRA 0.1% ~ 1% 低（12-24GB） 中等 消费级 GPU，资源受限
Adapter 1% ~ 5% 中等 快 多任务切换，模块化
Prefix-Tuning < 0.1% 最低 最快 生成任务，极端资源限制
06 — GUIDANCE & RECOMMENDATIONS

建筑师的指导性建议

就像建筑大师维特鲁威提出"坚固、实用、美观"三原则， SFT 的实施也有其核心指导原则。以下是基于第一性原理推导出的系统性建议。

这是 SFT 的第一原则，也是最常被违反的原则。1000 条精心标注的高质量数据， 往往比 100,000 条自动生成的低质量数据更有效。

实践建议：
① 投入至少 40% 的项目时间在数据质量和标注规范上；
② 建立多层质量审查：自动过滤 → 交叉验证 → 专家抽检；
③ 使用 LLM 辅助数据质量评估，但人工做最终裁决；
④ 对每条数据问：如果模型完美复现这条数据的行为，是我想要的吗？
不要一开始就试图用最复杂的数据和最高的参数。 建筑的逻辑是先打地基，再建框架，最后做精装修。

实践建议：
① 先用小规模（1-5K）高质量数据验证 pipeline 是否通畅；
② 确认基础效果后，逐步增加数据规模和任务复杂度；
③ 使用课程学习（Curriculum Learning）——从简单任务到复杂任务；
④ 每个阶段都做充分评估，确认方向正确后再进入下一阶段。
没有监控的训练就像没有安全检查的建筑工地——你不知道什么时候会出事。 好的监控体系能让你在问题发生之前就发现苗头。

实践建议：
① 实时监控 training loss 和 evaluation loss 的分离趋势（过拟合预警）；
② 定期生成样本（每 100-500 步），人工检查生成质量；
③ 在多个基准上跟踪性能变化（不仅仅是目标任务）；
④ 保存多个检查点，确保可以回滚到任何历史状态。
SFT 为模型注入了基础的指令遵循能力，但要达到生产级别， 通常需要配合后续的对齐技术形成完整的训练流水线。

实践建议：
① SFT → RLHF/DPO：使用人类偏好数据进一步优化输出质量；
② SFT → Iterative：建立数据飞轮，持续从线上反馈中改进；
③ SFT → Distillation：将大模型 SFT 的效果蒸馏到更小的部署模型；
④ 将 SFT 视为持续工程（Continuous Engineering），而非一次性项目。
建筑中，你不能改变重力定律。在 SFT 中，同样有一些不可逾越的限制。 尊重这些限制，而不是试图绕过它们。

实践建议：
① 数据上限定模型性能上限——不要期望模型超越训练数据的质量；
② 参数更新量与遗忘程度正相关——更多的改变意味着更多的副作用；
③ 模型没有"真正理解"——它在做高度复杂的模式匹配，请据此设计安全边界；
④ 分布外（OOD）输入永远是风险来源——部署时建立输入验证和输出过滤机制。

SFT 实施检查清单

在启动你的 SFT 项目之前，逐项确认以下要点：

  • ✓ 明确任务目标 — 清晰定义模型需要完成的具体行为，可量化的成功标准
  • ✓ 数据质量审计 — 完成数据来源审查、标注质量验证、多样性检查
  • ✓ 基座模型评估 — 在目标任务上评估候选基座模型的零样本/少样本性能
  • ✓ 计算资源规划 — 确认 GPU 显存、训练时长、存储空间满足需求
  • ✓ 评估体系就绪 — 自动评估基准 + 人工评估方案 + 安全测试用例
  • ✓ 回归测试基线 — 记录模型在通用基准上的初始性能，用于训练后对比
  • ✓ 监控与回滚方案 — 训练监控配置就绪，检查点保存策略已设定
